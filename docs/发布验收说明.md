# 0.1.0 / 0.1.1 / 0.1.2 / 0.1.3 发布验收说明

本文面向使用者与维护者，记录各版本的验证范围。普通使用步骤请读 README.md。下文第一至第三节是 0.1.0 首发时的原文记录，保持不变以便追溯；0.1.2 的更正内容、核验命令与结果见第四节；图片支持的离线范围见第五节，0.1.3 的打包核验见第六节。

## 结论

0.1.0 已完成发布前已知问题修复、用户文档、离线回归、实际 tarball 安装及独立 DSH Web profile 验收，可以作为首个开源版本交付。此结论表示源码与发行包已准备好，**不表示已经公开发布，也不表示所有服务商或其他宿主版本已验证**。

0.1.2 的结论见第四节：它修正了 0.1.1 发行包遗漏徽标诊断修复客户端的问题，并以真实安装包字节核验为准。

0.1.3 的结论见第六节：图片支持的 runtime 与测试字节已整合进发行源码，离线检查、完整测试与 tarball 临时目录离线安装通过；**未安装到实际使用中的 profile，也未做真机视觉验收**。

- 正常回答、取消前/取消中/切换前中止、首段输出后异常、缺失结束原因、异常错误码判据、确定性失败冷却和观察回调隔离均有自动化验证。
- 来源边界验证覆盖合法本机同源、伪造 Host/Origin、跨站标记、非 JSON 写入、IPv6/HTTPS 形态；真实回环 HTTP 请求验证读取、保存与冲突。
- 独立临时数据目录验证配置修订号、过期草稿拒绝、手工文件变更检测及完整保存；没有改动维护者的实际模型链或账号。
- Tabbit 使用真实页面和隔离 handler 验证输入、下拉同步、停用链保留、双页面冲突、保存失败保留草稿、不支持配置版本时禁用保存。

- 独立干净 DSH Web profile 安装实际发行包并正常启动；插件页中文名称可见，详情与设置入口均能打开同一编辑器。实际保存测试链成功，从另一入口保存后，旧页面的过期草稿被真实宿主拒绝且保留。最终包重新安装后再次保存通过。
- 全部运行测试没有调用外部模型服务。之前版本正常请求与自然降级的本机验收作为历史参考；首发修复的故障路径以可重复自动化证据为主。

独立复核又补齐取消终态的 failure 字段，锁清理不能覆盖成功结果、能力解析回环闸门、大请求413、目录不猜测模态、采样截断标记与用户提示。reasoning暂存是无痕降级机制的选择，README已明确说明；复核补充的七项回归纳入统一检查。

## 边界与使用建议

首发仅声明 DSH 0.2.1-rc.2、Node 24+、本机部署支持。Windows/Linux CI 已提供，但远端 CI 未运行前不宣称两种系统都完成真实宿主验收。Tabbit 截图通道发生超时，页面 DOM、交互和保存断言通过；不将截图失败包装成视觉验收成功。

运行状态是短期诊断，已开始作答不代表整轮成功。真实服务商权限、余额、网络和响应能力由用户自己的账号决定。避免虚拟链循环嵌套，优先使用真实渠道成员。

网页保存有修订号保护与进程间锁；手工编辑器不受锁约束，应避免在同一瞬间手工保存和网页保存。锁异常恢复和本机 HTTP 信任边界详见 SECURITY.md。

## 重新检查与打包

使用 Node 24+，执行 `npm run check`、`npm test`、`npm run release:prepare`。发布脚本导出公开清单内的干净源码，重新执行检查与测试，生成 tarball 后安装到临时目录验证，最后写入 SHA256SUMS 和机器可读报告。

公开仓库与发布附件应使用导出的 source 或源码压缩包，而非包含个人交接记录的开发工作目录。公开仓库为 https://github.com/sqx6781268/dsh-smart-route ，发行版使用 GitHub Releases；private=true 保留防误发 npm，不妨碍 GitHub 源码开源和 tarball 安装。

### 4.3 诊断开关的 origin 差异

诊断开关写入的是浏览器的 `localStorage`，按 **origin** 隔离：

- 桌面端窗口加载的页面 origin 固定为 `dsh-app://app/`，与本机 Web 服务端口无关；在这里设置一次即可长期有效。
- 用浏览器访问 `http://127.0.0.1:<端口>` 的 Web GUI 时，origin 含端口；换了端口需要在新的 origin 重新设置。

开启与关闭（刷新后生效）：

```js
localStorage.setItem('multi-chain:diagnostics', '1')   // 开启
localStorage.removeItem('multi-chain:diagnostics')     // 关闭
location.reload()
```

## 五、图片支持的离线验证（0.1.3 前身）

本节记录图片路由在隔离工作副本阶段的**离线**验证范围。这些结论随 0.1.3 一并进入发行包，但本节保留了当时的观测时点；0.1.3 的打包核验见第六节。

### 5.1 验证了什么（离线）

全部用宿主自带 Node 24 执行 `scripts/check.mjs` 与 `scripts/test.mjs` 得到，未调用外部模型服务、未把包安装到实际 profile、未改动桌面端或用户 profile。

- 项目检查：`scripts/check.mjs` 通过（发布清单、脚本语法、示例、语言与文档链接）。
- 统一测试入口：`scripts/test.mjs` 通过——路由基线 119 项、图片语义 **170 项**、徽标回归 39 项、待办增强 23 项、发布负例/网络/生命周期/复核 24 项，全部通过、0 失败。**数量以 `scripts/test.mjs` 的实际输出为准**；这里记录的是复审修复完成时的观测值，后续新增断言会使图片语义项数增长。
  - 计数演进（历史时点，保留以便追溯，不代表当前值）：初版实现时 133 项 → 取消语义修复后 162 项 → 复审修复后 170 项（复审修复补 M10b 冷却兜底失败路径、M7/M7b 告警中性表述后增至 170 项）。
- 图片语义测试（`test/image-selftest.mjs`）逐格对应 `docs/图片路由契约冻结.md` 的 M1–M27：全视觉链、混合链、全文本链、未知/解析失败、新图、历史图、tool 结果图、冷却轮转边界、取消（commit 前/后）、能力实时变化、宣称与筛选不一致、`IMAGE_OFFLOAD_REQUIRED` 透传、`UNSUPPORTED_CONTENT` 不冷却、结构判据负对照，以及 v2 收紧口径的守门格 M23–M27（image-only 不构成视觉资格、audio-only 不得改成 text、模态并集禁令）；另有取消语义修复补的取消三时机 M12a–M12g 与复审修复补的 R9 冷却兜底失败路径 M10b、告警中性表述 M7/M7b。
- **R9 冷却兜底的失败路径有独立守门格（M10b）**：唯一视觉成员预置冷却并以非冷却类码失败 → 兜底真的触发，断言纯文本成员从未被调用、终态 `ALL_CANDIDATES_FAILED`、日志含「都在冷却期」。已用变异体自证：把兜底判据改回 `candidates.length > 0` 后该格 3 条断言变红（**167 通过 / 3 失败**，即 170 − 3），复原后 **170 通过 / 0 失败**——证明它确实守住了"有图请求不因兜底回落文本成员"。
- 宿主两层投影的交互边界用桩复刻验证（不 import 宿主代码）：准入侧 `inputModalities` 不含 image ⇒ 以 `MODEL_DOES_NOT_SUPPORT_IMAGES` 拒绝；请求投影侧不含 image ⇒ 历史图片块被替换成 `textOnlyImageText` 占位文本，且该投影发生在插件之前，插件"看不到原图"这一边界由此得到固定；`inputModalities` 缺省（未知）时两道门都不动作，这也是插件必须返回具体模态数组的原因。
- 运行状态消费方：`resolveModel`/`#run` 的筛选结果走既有有界记录（上限 100 条），`/api/status` 暴露 `lastVisionSkip`，记录只含成员与固定原因码（`NO_VISION` / `NO_VISION_MEMBER`），断言确认不含图片内容、提示词或凭据。

### 5.2 没有验证什么（不得当作已通过）

- **没有真机视觉对照**：没有在真实宿主里选择链、上传图片并观察模型实际回答，因此不宣称任何具体模型或渠道"真的能看图"。
- **没有对真实服务商发图片请求**：成员是否能接受某种图片格式/尺寸，仍由各服务商与成员适配器决定。
- **纯文本链的历史图不可恢复**：这是宿主契约行为（投影发生在插件之前），不是本轮能修的缺陷，也不承诺修复。
