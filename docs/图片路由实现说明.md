# 图片路由实现说明（设计文档）

> **目的**：记录"链的图片支持"在代码里**怎么落地**——判据放在哪、为什么这样放、与契约条目怎么对应，供独立验证、审查和后续维护对照。
> **权威口径**：需求条目以 [`docs/图片路由契约冻结.md`](图片路由契约冻结.md) **v2** 为准（R1–R12、R2b、B1–B4、M1–M27）。本文件只解释实现，**不新增需求**；两者冲突时以契约为准并修正本文件。
> **当前状态**：图片支持已随 **0.1.3** 进入源码与发行包，离线检查、完整测试与 tarball 离线安装冒烟均通过；仍**没有**真机视觉验收，未对真实服务商发过图片请求。

---

## 一、一句话结论

图片能力是**额外宣称**：视觉资格 = 成员**本次实时**同时声明 `text` 与 `image`。链只在这种情况下宣称 `text + image`，含图片的请求只委派给这些成员；没有这类成员就**明确报错**（`NO_VISION_MEMBER`），不丢图、不图转文、不改用文本成员。纯文本请求的候选顺序与降级逻辑**一字未改**。

## 二、四个落点（`src/adapter.mjs`）

| 位置 | 职责 | 对应契约 |
|---|---|---|
| `isVisionMember(modalities)` | 视觉资格的唯一判据：`Array.isArray` 且**同时**含 `'text'` 与 `'image'`。宣称与筛选**共用**它，避免两处判据分叉 | R2、R3、R8、B4 |
| `contentRequiresVision(content)` / `messagesRequireVision(messages)` | 结构判据：只看消息 `content` 数组里 `type === 'image'` 的块，覆盖**全部**消息（含 `role:'tool'`）。不做字符串搜索、不做递归、不只看最后一条 | R6、R7、M8、M9、M19、M22 |
| `resolveInputModalities(infos)` | 三段算法：① 非 image 模态取交集（视觉成员的 `image` 不进交集）② 有视觉成员才追加 `image` ③ 交集为空/未知兜底 `['text']`，已知非空原样保留 | R2、R2b、R5、B2、M23–M27 |
| `resolveMemberInfos(deps, members, signal)` | 每个成员**本次实时** `llm.resolveModelInfo`；抛错记告警并按"非视觉"处理，能力回环仍上抛 | R3、R4、M7、M14、M15 |
| `#run` 的筛选段 | `orderCandidates` → 去自引用 → **有图则只留视觉成员** → 冷却过滤 → 兜底；兜底集合是**已筛集合** | R8、R9、M3、M4、M10、M11 |
| `carriesImageOffload` / `preserveFailure` | `IMAGE_OFFLOAD_REQUIRED` 的 failure 按宿主白名单**原样**搬运，且该成员不降级、不进冷却 | R10、M16 |

### 2.1 为什么 `image` 不进交集

基线是"模态取交集"。若沿用交集：混合链（视觉 A + 文本 B）会宣称 `['text']`，宿主随即在 `dsh-llm:2337` 把历史图片块投影成占位文本——发生在插件看到 `messages` **之前**，于是链里的视觉成员**永远**收不到图（B2）。所以视觉成员的 `image` 单独走"额外宣称"通道；其余模态仍严格取交集，**不是**并集（M27 守住）。

### 2.2 为什么视觉资格要求 `text` **且** `image`

只声明 `['image']` 的成员拿不到整段文本历史，把图片请求给它必然失败；把它当视觉成员还会让链错误宣称图片能力（M23）。反之 audio-only 链必须如实声明 `['audio']`，不能灌成 `['text']`——那会让宿主误判成"可发文本"（R2b / M24 / M25）。

### 2.3 为什么 `inputModalities` 必须是具体数组

宿主把 `inputModalities === undefined` 当"未知"：**既不投影也不拒绝**（`dsh-llm:2337`、`session-controller:940` 两个判据都要求显式声明且不含 image）。所以"没有视觉成员"时也必须给出具体数组（`['text']` 或原样交集），否则发图请求会被静默放行（R5）。

## 三、纯文本路径为什么零回归

- `messagesRequireVision(options.messages)` 为假时，`#run` **不进入**筛选分支，也**不**额外调用 `resolveModelInfo`：候选顺序、冷却、"全员冷却仍全试"、commit 缓冲、取消终态全部沿用基线代码路径（R1）。
- `resolveModel` 的窗口取最小、输出上限取最小、`reasoning.efforts` 取交集都保留；只有 `inputModalities` 的 image 部分改为额外宣称（M1/M2 的断言里同时检查了这三项）。
- 既有 119 项基线断言未放宽，只把「模态取交集」那条 image 断言按 v2 改为"混合链宣称 `text+image`"。

## 四、运行记录（消费方覆盖）

- 适配器只投递**固定码**：`{kind:'skip', code:'NO_VISION'}`（成员被跳过）与 `{kind:'skip', code:'NO_VISION_MEMBER'}`（链级拒绝），字段只有 `kind/chain/sessionId/provider/model/time/code`——**不含**图片内容、提示词或凭据。
- `src/index.mjs` 的 `runtimeStatus()` 增加 `lastVisionSkip`；`latest`/`lastDegrade`/`lastServed` 语义不变。
- `src/editor.html` 的运行状态表增加「图片筛选」列，`routeLabel()` 增加 `skip → 跳过成员`。能力展示（窗口/输出/模态）**未改**。
- 记录仍受既有的**有界**上限（100 条）约束，与基线一致。

### 5.1 M10b 为什么必须单独一格

M10 只测"A 冷却但 A 成功"——兜底分支从未真正触发；M11 的视觉成员没预置冷却（`usable.length ≠ 0`），兜底也不进入。于是"兜底集合是**已筛视觉集合**还是**原候选**"这条判据长期零覆盖：把判据改回 `candidates.length > 0 → ordered = candidates`，原有全部用例仍全绿，但实际会把**含图请求交给纯文本成员**（正面违反 R9）。M10b 用"唯一视觉成员预置冷却 + 以非冷却类码失败"逼兜底真的触发，并以变异体自证（变异 → 该格 3 条断言红；复原 → 全绿）。

## 六、明确的未覆盖边界

1. **纯文本链的历史图不可恢复**：给不宣称 image 的链发请求时，宿主在插件之前把历史图片块换成 `[image omitted because this model accepts text only; attachment sha256:…]`。插件收到时已无原图，**检测不到也无法恢复**。可承诺的只有"用声明了图片能力的链保留历史图"（B1）。
2. **没有真机视觉对照**：未在真实宿主里选链、上传图片并观察模型回答，也未对任何服务商发图片请求；因此不宣称任何模型/渠道"实际能看图"。
3. **成员自己的图片预算仍由成员执行**：插件不自造数量/字节预算，不做缩放或重编码；`imageRequestPricing` 仍返回 `undefined`、`imageRequestTarget` 仍原样回交（R11）。
4. **安装后行为只在临时目录验证**：0.1.3 打包时已运行 `scripts/install-smoke.mjs`，在全新临时目录离线安装 tarball 并检查导出、入口、语言、编辑器、Schema 与许可证；**未**把该包安装到任何实际使用中的 profile，也不代表真机视觉可用。
5. **宿主版本限定**：所有宿主行号引自 DSH 0.2.1-rc.2 的现场提取副本（见契约第二节）；其它宿主版本的行为不在本文件承诺范围。
