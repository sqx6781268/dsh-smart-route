## 一、结论摘要（先看这一段）

1. **文本路由一个字都不改**：无图片历史的请求，候选顺序、降级判据、冷却、"全冷却时仍全试"、commit 缓冲全部沿用现规则（`src/adapter.mjs` 基线行为）。
2. **视觉资格 = 同时具备 `text` 与 `image`**：链只有在**本次实时**解析出至少一个成员**明确同时声明** `'text'` 与 `'image'` 时，才额外宣称 `image`；只声明 `['image']` 的成员**不**构成视觉资格。非 image 模态一律按原交集规则，**不**做"凡不是 image 就当 text"的归一化。
3. **图片请求按成员筛**：本次请求的**全部有效消息**（含 tool 角色结果）里只要存在真实图片块，`#run` 委派前就只保留**视觉成员**（同时含 text+image）；纯文本请求保持原顺序。
4. **无视觉成员 → 明确报错**：给出可诊断的终态错误，**绝不**把图片转成文字、**绝不**因为没视觉就自动改用文本成员。
5. **未知/解析失败不当视觉**：`resolveModelInfo` 抛错、`inputModalities` 缺失、非法或不同时含 text+image，一律按"非视觉"处理（宣称与筛选都如此），不缓存成"可能能看图"。
6. **预算与契约保守**：`imageRequestPricing` 继续返回 `undefined`（中性估算），`imageRequestTarget` 继续原样回交尺寸/字节，不自造图片数量或字节预算；`IMAGE_OFFLOAD_REQUIRED` 必须**带着 `offloadImages` 原样上抛**，否则宿主的图片卸载恢复链会断。
7. **必须写明的边界**：若一条链**不宣称 image**，宿主的图片→占位文本投影发生在**插件看到 messages 之前**，插件既检测不到也恢复不了；这是宿主契约，不是本插件能承诺修复的能力。

## 三、冻结需求（可测条目）

### R1 文本路由零回归
- 请求历史**不含**图片块时，`#run` 的候选顺序、降级判据、冷却跳过、"全部冷却则仍全试"、commit 缓冲与取消终态**与基线逐项相同**。
- 判据：`test/selftest.mjs` 全部既有用例（基线 119 通过 / 0 失败）**不加修改**继续通过；不得为了让新用例过而放宽旧断言。

### R2 图片能力"额外宣称"，视觉资格必须同时含 `text` 与 `image`

> **v2 修正（2026-10-25，captain 转达原批准范围）**：v1 把视觉资格写成"`includes('image')`"即算，**过宽**。原批准范围要求视觉资格**明确同时含 `text` + `image`**：只声明 `['image']`（纯图像输入）的成员**不**构成视觉资格。同时 v1 "没 image 就声明 `['text']`" 的表述**过宽**，会把 audio-only 等成员无条件改成 text —— 一并收紧。

链的 `resolveModel` 返回值按以下**三段**计算，顺序固定、互不越界：

1. **非 image 模态部分**：严格沿用基线交集规则 —— 只统计"本次实时解析成功且 `inputModalities` 是合法数组"的成员，对它们取**交集**。**不得**因为要宣称 image 而改动这部分（不许加、不许删、不许改成并集）。
2. **image 追加条件**：仅当**至少一个成员本次实时**解析出的 `inputModalities` **同时包含 `'text'` 与 `'image'`** 时，才追加 `'image'`。只有 `'image'` 而无 `'text'` 的成员**不**构成视觉资格（按 R2b 处理）。
3. **缺省兜底**：仅当非 image 部分因"所有成员都未知"而为空/未定义时，声明 `['text']`（保守：视为可发文本、**不可**发图，见 R5）。但若交集**已知且非空却不含 `text`**（例如 audio-only 链得到 `['audio']`），**必须原样保留该交集**，不得改成 `['text']`，也不得追加 `'image'`。

- 判据：结果里 `'image'` 的出现**当且仅当**存在成员实时声明**同时含 `text` 与 `image`**；`contextWindow`/`defaultMaxTokens` 仍取**最小**；`reasoning.efforts` 仍取**交集**（这三项一个都不许改成并集）；`'audio'` 等非 text/image 模态只在第 1 段交集里出现，插件永不增删。

### R2b 非 image 模态不得被"无条件改成 text"
- 插件**不**做"凡不是 image 就当 text"的归一化；成员/链声明什么模态，就在交集范围内如实反映。
- **反例（出现即判失败）**：成员只有 `['audio']`，而链对外声明 `['text']` 或 `['text','image']`。
- **正例**：`['audio']` 成员单独成链 ⇒ 声明 `['audio']`；图片请求按"不含 image"被宿主投影/拒绝，符合预期。
- 同理：`['image']` 单独成员 ⇒ 交集为 `['image']`，**不**补 `text`、**不**产生视觉资格（它拿不到 text 输入，不是"视觉成员"）。

### R3 未知/解析失败不当视觉
- `resolveModelInfo` 抛错、返回非数组、数组含非法值、或数组**不同时含 `text` 与 `image`** ⇒ 该成员**在宣称与筛选中都按非视觉**处理；并在日志里保留既有"无法解析能力"告警语义。
- 判据：桩 `resolveModelInfo` 抛错时，链不宣称 `image`；有图请求不把该成员当候选；桩返回 `['image']`（无 text）时同样不构成视觉资格。

### R4 能力解析必须用"本次实时"元数据
- 路由决策只能读取**本次请求**通过 `llm.resolveModelInfo` 得到的值；**禁止**读取 `~/.dsh/multi-chain/capabilities.json` 或任何进程启动期快照来决定"谁能看图"。
- 判据：同一进程内连续两次请求，桩第二次把 `inputModalities` 从 `['text','image']` 改成 `['text']`，第二次的有图请求**必须**按"无视觉成员"处理（见 M9）；且整个模块运行期不得出现对 `CAPABILITIES_FILE` 的读取（可用桩 fs/注入断言，或源码级断言"能力决策路径不读该文件"）。

### R5 没有视觉时"明确拒绝"，不得静默放行或图转文
- 链不宣称 `image` 时，**必须**让 `inputModalities` 是个具体数组而不是 `undefined`，使宿主的两道门（准入 `session-controller:940` / 投影 `dsh-llm:2337`）都按"不含 image"处理：
  - 交集**含 `text`**（纯文本链、混合但无视觉候选、成员全未知）⇒ 声明 `['text']`，宿主以 `MODEL_DOES_NOT_SUPPORT_IMAGES` 明确拒绝发图；
  - 交集**不含 `text`**（如 audio-only 链）⇒ 原样声明该交集（如 `['audio']`），**不得**灌成 `['text']`（R2b）；宿主同样因"不含 image"拒绝，且不会误判成可发文本。
- 若图片仍进入了 `#run`（例如会话中途从视觉链切到纯文本链、历史里带图），而筛选后**没有**视觉成员：给出终态错误，错误码独立（`NO_VISION_MEMBER`）、消息里点名链 id 与"无成员同时声明 text 与 image"，**不委派**任何成员，**不**把图片替换成文本，**不**试图"能跑就行"。

### R6 结构检测：只认真实图片块
- 判据必须是"消息 `content` 数组里存在 `type === 'image'` 的块"；**禁止**：`JSON.stringify(...).includes('"image"')` 之类字符串搜索；对任意对象/深层嵌套的递归扫描（`tool-call.arguments` 里的 JSON 字符串、`replayState`、`meta` 等一律不看）；只看最后一条或只看 `user` 角色。
- `type === 'file'` **不算**图片（宿主已把它投影成文本句柄，见 2.1）。
- 保守选择：`offloaded: true` 的图片块**仍算图片**。理由：成员适配器可能拒绝历史中的图片块（`dsh-llm-pi-ai/lib/index.js:1216` 用 `contentHasImage`，**包含** offloaded），把它当文本会让委派直接 `UNSUPPORTED_CONTENT`。

### R7 覆盖"全部有效消息"（含 tool 结果）
- 检测范围 = 本次请求 `options.messages` 的**全部条目**，逐条看 `content`；`role === 'tool'` 的 tool-result 正文同样在 `content` 里，必须一并覆盖；不看 `system`/`tools` 之外的旁路字段。
- 判据：仅"第一条 user 有图"、仅"中间 tool 结果有图"、仅"最后一条 user 有图"三种位置都必须被检出（M6/M7）。

### R8 委派前按视觉筛选，纯文本保持原顺序
- **"视觉成员"定义（v2 收紧）**：本次实时 `inputModalities` **同时含 `text` 与 `image`** 的成员。只有 `image`（无 text）的成员**不是**视觉候选 —— 给它发整段文本历史本就不可行。
- 顺序：`orderCandidates(chain)`（含 round-robin）→ 去自引用 → **若历史有图，则只保留视觉成员** → 冷却过滤 → "全部冷却"兜底。
- 筛选只做**删除**，不重排；纯文本请求不进入该分支。

### R9 冷却兜底不越界
- "全部成员都在冷却时仍全试"的兜底集合**必须**是"已按视觉筛过的集合"；有图请求**永不**因为兜底而重新引入纯文本成员。
- 判据：视觉成员 A 冷却 + 纯文本成员 B 可用 + 有图请求 ⇒ 仍只试 A（M8）。

### R10 `IMAGE_OFFLOAD_REQUIRED` 必须原样连续

## 四、边界（必须写进文档，不能承诺）

### B1 纯文本链处理"历史图片"时，宿主先投影，插件不可见
给一条**不宣称 image** 的链发请求时，宿主在 `adapterStream` 里、**插件 `stream()` 之前**执行 `:2337 → :745`，把每个图片块换成 `textOnlyImageText` 占位文本（`[image omitted because this model accepts text only; attachment sha256:…]`）。

- 插件收到的是**已经被替换过的** messages：**检测不到**原图，**无法**把它交给视觉成员，也**无权**声称"能恢复"。
- 该投影是**请求级**的（不写日志、不改会话历史），所以切回一条**宣称 image** 的链后，后续请求仍能看到原图。
- 因此文档口径只能是：**要在多轮会话中保留历史图片，请使用声明了图片能力的链**（混合链也算，见 B2）；不承诺"纯文本链也能继续看图"。

### B2 混合链必须宣称 image
链里只要有一个成员**同时声明 `text` 与 `image`**，就必须宣称 `['text','image']`。否则（若按交集只留 `text`）宿主会在 B1 处把历史图替换成占位文本，混合链里的视觉成员**永远**收不到图，能力形同虚设。
代价是：混合链里的纯文本成员在有图请求中**被筛掉**（R8），这正是必须写清的"能力与代价"。

### B3 声明与路由是同一次请求内的两处解析
`resolveModel`（宿主用于准入与投影）与 `#run`（插件用于筛选）各自调用 `resolveModelInfo`。若两次之间有元数据变化，可能出现"宣称 image、筛选后为空"——此时按 R5 明确报错，**不许**退化成纯文本请求（那会触发 B1 的静默图转文）。

### B4 "明确声明"的口径（v2 收紧）
只认宿主 `resolveModelInfo` 返回的 `inputModalities` 数组里**同时**出现 `'text'` 与 `'image'`。目录（`listModels`）里的 `inputModalities` **不作为**路由依据（沿用"目录不猜测能力"），也不认任何文件名、模型名、注释里的"vision"字样。宿主类型层面只有 `'text'` 与 `'image'` 两个合法值（`typert.host.js:21` `z.union([z.literal("text"), z.literal("image")])`），但第三方适配器不受该 schema 约束，因此 R2b 的"audio-only 不得当 text"必须由测试守住。

## 八、取消语义修复记录（只追加）

### 8.1 缺陷

图片筛选在 `#run` 中新增了 `await resolveMemberInfos(...)` 这段能力解析。取消若落在这段窗口内，`resolveMemberInfos` 的 catch 把 `AbortError` / `ABORTED` / `ABORT_ERR` 当普通解析失败吞掉 → `visual` 为空 → 终态 `NO_VISION_MEMBER`。后果：用户主动取消被伪装成"链不支持图片"，且与"未取消且确实无视觉成员"**终态不可区分**——M12（取消必须给 `aborted` + 完整 `failure`）在该路径不成立。

### 8.2 修复（两处，最小改动）

1. `resolveMemberInfos` 的 catch 对取消**直接 rethrow**（判据抽成 `isAbortError`，与 `exceptionFinish` 同口径：`name === 'AbortError'` / `code === 'ABORTED'` / `code === 'ABORT_ERR'`）。取消不再被归类为"能力未知"。
2. `#run` 把该 `await` 包进 try/catch，由插件自己 `yield abortedFinish()`，**不让裸异常逸出生成器**（否则宿主按 `error` 记这一轮）；解析正常返回后**再补一次** `options.signal?.aborted` 检查，覆盖"解析忽略 signal、稍后才成功返回"。

### 8.3 回归证据

- 新增 M12a–M12g（`test/image-selftest.mjs`，图片语义 133 → **162 项 / 0 失败**）：解析阶段取消三种错误形态、入口已取消、循环中取消、解析忽略 signal 后成功返回、signal 未取消但成员抛取消码——均断言 `{kind:'aborted', failure:{code:'ABORTED', message}}`、零委派、不冷却；另加正对照（未取消且确实无视觉仍为 `NO_VISION_MEMBER`，`kind:'error'`）与轮转 A/B 对照。
